## Light-Mode

- **[hoch] Ungültige rgba()-Misch-Syntax: Glass-Hintergründe, -Borders und Accent-Glows fallen komplett aus** — `resources/css/app.css`
  Die Glass-Variablen sind space-separierte RGB-Tripel (--card-rgb: 255 255 255), werden aber in Komma-Syntax verwendet: rgba(var(--card-rgb), 0.65) ergibt nach Substitution rgba(255 255 255, 0.65). Das ist per CSS Color 4 ungültig (Legacy-Syntax verlangt Kommas zwischen allen Kanälen, moderne Syntax Slash vor Alpha) — alle Engines verwerfen den Wert. Da der Fehler erst bei var()-Substitution auftritt (invalid at computed-value time), fällt die ganze Property auf initial zurück. Betroffen: .glass background/border/border-top-color (Z. 70, 73–74), .glass-subtle background/border-bottom (Z. 83, 86), .glass-btn background/border + Hover (Z. 94, 97, 101–103), .accent-glow (Z. 109–110), .np-btn-primary Hover-Glow (Z. 137–138) und der Body-Tiefen-Gradient (Z. 29–30). Im Light-Mode heisst das: Panels haben weder Füllung noch Rahmen und sind auf dem fast weissen --bg nur noch am Schatten erkennbar; .accent-glow und der Primär-Button-Glow sind wirkungslos. Nur backdrop-filter und die rgba(0,0,0,…)/rgba(255,255,255,…)-Schatten (echte Komma-Syntax) funktionieren — dadurch fiel der Defekt im Dark-Mode kaum auf.
  Fix: Überall auf Slash-Syntax umstellen: rgb(var(--card-rgb) / 0.65), rgb(var(--glass-border) / var(--glass-border-alpha)), rgb(var(--glass-border) / calc(var(--glass-border-alpha) * 1.6)), rgb(var(--accent-rgb) / 0.16) usw. — analog zu den bereits korrekten Stellen Z. 47/150–151 (rgb(var(--accent) / 0.25)). Danach npm run build.

## Korrektheit/Sicherheit

- **[mittel] CSV-Formel-Injection in allen fünf CSV-Exporten** — `app/Http/Controllers/Lernender/NotenController.php`
  Alle CSV-Exporte schreiben Benutzereingaben ungefiltert via fputcsv: noten.titel (freier Lernenden-Input, max 150 Zeichen) sowie vorname/nachname. Beginnt ein Wert mit =, +, - oder @, interpretiert Excel ihn beim Oeffnen als Formel (CWE-1236). Angriffsvektor: Ein Lernender erfasst eine Note mit Titel wie =HYPERLINK(...) oder =cmd|... — der Berufsbildner oder Admin oeffnet den Export in Excel und die Formel wird ausgefuehrt. Betroffen: Lernender/NotenController.php export() Zeile 521-537, Berufsbildner/NotenController.php export() Zeile 256-272 und exportAlle() Zeile 325-343, Admin/NotenController.php export() Zeile 327-346, Admin/BerichtController.php notenExport() Zeile 225-242.
  Fix: Zentralen Helper einfuehren (z.B. App\Support\Csv::safe($value)): wenn der Wert mit =, +, -, @, Tab oder CR beginnt, ein Apostroph (') voranstellen. In allen fputcsv-Aufrufen auf titel, vorname, nachname, fachModul anwenden.
- **[mittel] Hardcodierte Rollen-ID 2 fuer Berufsbildner-Profil bei Benutzeranlage** — `app/Http/Controllers/Admin/BenutzerController.php`
  In store() wird das berufsbildner-Profil nur angelegt, wenn `$rolleId === 2` — die ID ist hardcodiert, waehrend die Lernender-Rolle vier Zeilen darueber korrekt dynamisch via `DB::table('rollen')->where('name', 'Lernender')` aufgeloest wird. In der aktuellen DB ist 2 = Berufsbildner, aber bei abweichender Seed-Reihenfolge (Neuinstallation, Test-DB) erhaelt ein Benutzer mit BB-Rolle kein berufsbildner-Profil: Alle BB-Controller pruefen `$user->berufsbildner` und werfen 403 — der Benutzer kann sich einloggen, aber nichts tun. Umgekehrt koennte eine andere Rolle faelschlich ein BB-Profil erhalten.
  Fix: Analog zur Lernender-Logik: `$bbRolleId = (int) DB::table('rollen')->where('name', 'Berufsbildner')->value('rolle_id');` und dann `if ($rolleId === $bbRolleId)` statt `if ($rolleId === 2)`.
- **[mittel] Admin-Profil-Update erlaubt NULL fuer NOT-NULL-Spalten — SQL-Fehler 500 statt Validierungsmeldung** — `app/Http/Controllers/Admin/LernendeController.php`
  updateProfil() validiert lehrberuf_id und lehrbeginn als nullable und schreibt `$validated['lehrberuf_id'] ?? null` bzw. `$validated['lehrbeginn'] ?? null` in die Tabelle lernende. Im DB-Schema sind beide Spalten aber NOT NULL (verifiziert via SHOW COLUMNS). Der BB-Controller (Berufsbildner/LernendeController.php update(), Zeile 287-290) macht es korrekt mit 'required'.
  Fix: Validierungsregeln auf `'lehrberuf_id' => ['required', 'integer', 'exists:...']` und `'lehrbeginn' => ['required', 'date']` aendern — konsistent mit dem BB-Pendant. lehrende darf nullable bleiben.
- **[mittel] Deaktivierte Benutzer bleiben mit bestehender Session voll handlungsfaehig** — `app/Http/Requests/Auth/LoginRequest.php`
  Das Flag benutzer.aktiv wird ausschliesslich beim Login geprueft (credentials() ergaenzt 'aktiv' => 1). Deaktiviert ein Admin einen Benutzer via toggleAktiv (Admin/BenutzerController.php Zeile 227), bleibt dessen laufende Session unberuehrt: Der Benutzer kann bis zum Session-Ablauf (Standard 120 Min.) weiter Noten erfassen, kommentieren und exportieren.
